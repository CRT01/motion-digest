# 动效简报 · 2026-10-12

今天三件事。头条是 Emil Kowalski 在 skills 仓库新增的 `/animation-performance`：专门诊断「为什么掉帧」，不谈缓动品味，只谈帧预算、属性层级、主线程与 `will-change`。其次是 Motion **14.1.0**：`animateLayout` 正式进主包，给 vanilla JS 做布局动画和 `data-layout-id` 共享元素。第三是 Emil 10-09 的体感规则：越大/越远就越慢——质量感与路程决定时长。盯着的 AlphaXe、LottieFiles skill、gsap-skills、mblode（本周是 PR 工具链）、优设/ISUX 本窗口没有新产品动效 keeper；一批「动效视频导演 / AE 替代」仓库（如 `roc00/motion-design-workbench`、`zoih6/Nezarmotion`）按车道直接剔除。

### [animation-performance（Emil 掉帧诊断 Skill）](https://github.com/emilkowalski/skills/tree/main/skills/animation-performance)

**类型：** skill

**是什么。** Emil Kowalski 的 `emilkowalski/skills` 在 2026-10-11 新增 `/animation-performance`（同日 [X 说明](https://x.com/emilkowalski/status/2109277388437868623)）。它只做一件事：让动效落在帧预算内。不选缓动/时长（那是 `/animate`），不评判该不该动（那是 `/review-animations`），也不管 React Native 线程（那是 `/animate-expo`）。开场只回一句就绪语，等你描述卡顿现象。硬规则包括：默认只动 `transform`/`opacity`；先命名原因再改代码；永远不要用「我电脑上很顺」结案；禁止 `transition: all`；别把正确性换成「尽量硬件加速」。症状表把卡顿、阴影抖、导航时掉帧、Motion `x`/`y` 掉帧、手写 rAF 掉帧、列表变长后拖拽变糊、`blur` 卡、意外属性在动、起止 1px 跳，映射到对应修法。帧预算按 60fps = 16.7ms、120Hz = 8ms 写死。属性分三档：Composite（`transform`/`opacity`，以及部分浏览器的 `filter`/`clip-path`/`background-color`）→ Paint（`box-shadow`/`border-radius`/`color`）→ Layout（宽高边距定位）。换档表很实用：宽高→`scale()`，位移→`translate()`，显隐→`opacity`，阴影→`filter: drop-shadow()`。主线程章节对比 rAF / WAAPI / CSS：页面忙的时候（路由、hydration、拉数）优先 CSS 或 WAAPI；Motion 的 `x`/`y`/`scale` shorthand 走 CSS 变量所以**不**加速，忙线程场景要写成 `transform: "translateX(…)"` 字符串。还点名两个「看着对其实掉帧」的陷阱：继承 CSS 变量（Vaul 拖拽变慢的根因）和动画 `blur()` 超过约 20px（Safari 尤其）。`will-change` 只在看见起止跳或测到掉帧后再加，且只挂在真正在动的那个元素上。

**何时用。** 动效卡顿、掉帧、导航时指示条抖，或 agent 写完动画却没做过性能审查；装 `npx skills add emilkowalski/skills` 后调 `/animation-performance`。

**可带走的一点。** **忙主线程时别用 Motion 的 `x`/`y` shorthand——改 `animate={{ transform: "translateX(100px)" }}` 才能走硬件加速；阴影别直接动 `box-shadow`，用 `filter: drop-shadow()`。** 诊断顺序：先查属性档位 → 是否碰上页面忙 → 是否每帧 `setState` → 内容变多是否更糊（继承变量）→ `blur` 是否过大 → 最后才 `will-change`。

### [Motion 14.1.0（animateLayout 进主包）](https://motion.dev/changelog?lib=motion#14-1-0)

**类型：** 库

**是什么。** Motion **14.1.0**（2026-10-09）把原先 Early Access / `motion-plus` 里的布局动画 API 正式导出为 `import { animateLayout } from "motion"`（亦从 `framer-motion/dom`、`motion-dom` 导出）。文档见 [Layout animations](https://motion.dev/docs/layout-animations)：在 `animateLayout(() => { /* 改 DOM */ })` 里改布局，带 `data-layout` 的元素会动画到新的尺寸与位置，连 `justify-content: flex-start ↔ flex-end` 这类通常不可插值的 CSS 值也能动。可选第一参数做作用域（选择器或元素）；传 Motion transition（如 `{ type: "spring" }`）配置手感。共享元素用匹配的 `data-layout-id`：拆掉旧节点、挂上同 id 的新节点即可「魔术移动」（Tab 下划线一类）。示例：[js layout](https://motion.dev/examples/js-layout-animation)、[shared layout](https://motion.dev/examples/js-shared-layout-animation)。同版本还修了：主线程被占时延迟开启动画防视觉跳变、Fast Refresh 后 `whileHover`/`whileTap` 粘住、`scroll`/`useScroll` 弹性 overscroll 报告、`AnimatePresence` 在 iframe/另一窗口的 `popLayout`、暂停后非 1 倍速播放跳帧，以及拖拽元素内部的 layout 动画。下一小版本前，10-09 简报里说的「layout-in-drag / popLayout 等」已进 changelog。

**何时用。** 非 React（或非 `motion` 组件树）也要做布局动画 / 共享元素；或要从 `motion-plus` 的 `unstable_animateLayout` 迁到主包。

**可带走的一点。** **需要 `motion@14.1.0+`；布局变化包进 `animateLayout`，元素打 `data-layout`，跨节点用同一 `data-layout-id`。** 只改位置可 `data-layout="position"`，要保宽高比用 `preserve-aspect`。

### [越大越慢、越远越长（Emil 体感规则）](https://x.com/emilkowalski/status/2108531407786242389)

**类型：** 设计哲学

**是什么。** Emil 在 2026-10-09 的短帖把「质量感」写成可执行的调时规则：动画元素越大，移动应越慢——大物体看起来更重；同样，路程越远，时长应越长。配图对比：右侧大手比左侧一堆小光标慢得多，否则大块会显得发飘、小控件会显得拖沓。这条和「UI 动效通常 &lt; 300ms」不矛盾：300ms 是产品交互上限的经验值，尺寸与路程决定的是**相对**快慢——大抽屉滑入可以比小 Toast 略长，短距离微反馈应明显短于跨屏共享元素。

**何时用。** 调弹簧/时长时觉得「大卡片飞得太轻」或「小图标挪得太肉」，或审查 agent 给所有元素塞同一 `duration`。

**可带走的一点。** **同一套 token 里按尺寸分档：微控件短、大面板略长；路程加倍时先加时长，而不是只加 bounce。** 高频小操作仍优先缩短或干脆不动（与 Emil 的「You Don't Need Animations」同一条品味轴）。
